# ADR-0004. 채팅방 멤버십은 저장하지 않고 주체(모임/일정)의 참여자에서 파생

- 상태: 채택
- 날짜: 2026-09-11
- 관련: #17, #18, ADR-0002

## 맥락

채팅방은 모임과 일정에 하나씩 자동 생성되고, "모임 참여 = 채팅방 참여" 로 정했다.
그렇다면 `chat_room_members` 테이블이 필요한가?

## 검토한 대안

| 방식 | 판단 | 이유 |
|---|---|---|
| `chat_room_members` 테이블을 두고 참여/퇴장 시 동기화 | 기각 | 모임 참여·퇴장·역할 변경·일정 참여·취소·회원 탈퇴(#48) **모든 경로**에서 두 테이블을 함께 갱신해야 한다. 하나라도 빠지면 "모임은 나갔는데 채팅은 보이는" 상태가 되고, 이런 어긋남은 발견이 늦다. 이 프로젝트는 파생 데이터를 저장하지 않는 원칙을 따른다 (일정 참여자의 모임 소속 여부도 조인으로 판정). |
| **멤버십을 참여자 테이블에서 파생** | **채택** | 채팅방 → 주체(roomType + ownerTsid) → 그 주체의 참여자 테이블을 조회하면 끝. 동기화할 것이 없다. |

## 결정

- `chat_rooms` 는 `room_type` 과 `gathering_tsid` / `schedule_tsid` 로 주체를 가리킨다. **타입은 명시 컬럼**이다 — 어느 FK 가 null 이 아닌지로 추론하지 않는다 (분기 조건이 스키마에 의존하지 않도록).
- 멤버십 판정: `GATHERING` 이면 `gathering_participants`, `SCHEDULE` 이면 `schedule_participants` 에 `(owner_tsid, user_tsid)` 가 있는가. 타입별로 명시 분기하며 `else` 로 뭉개지 않는다.
- "내 채팅방 목록" 은 내가 참여한 모임의 방 ∪ 내가 참여한 일정의 방. 쿼리 두 번 또는 UNION 한 번.
- 읽음 위치는 멤버십과 별개로 필요하므로 Cassandra 의 `chat_room_read_positions_by_user (user_tsid, room_tsid, last_read_message_tsid)` 에 둔다 (ADR-0002). 이 row 는 "멤버" 가 아니라 "이 사용자가 이 방을 여기까지 읽었다" 는 **워터마크**다. 처음 읽을 때 생성되고, 뒤로 가지 않는다.
- 워터마크는 메시지를 참조하지 않는다. TSID 가 시간순이므로 그 메시지가 없어져도 "이 시점 이후" 라는 의미는 유지된다.

## 결과

- 모임/일정 참여자가 바뀌면 채팅방 멤버십은 즉시, 저절로 바뀐다. 동기화 코드가 없다.
- 멤버십 검증이 참여자 테이블 조회 한 번을 추가한다 — PK/uk 조회라 비용은 무시할 수 있다.
- 주체가 늘어나면(예: 지역 채팅) `ChatRoomType` 에 값을 추가하고 판정 분기를 하나 더 쓴다. `switch` 가 exhaustive 하므로 빠뜨리면 컴파일 에러다.
